# Phase 2 产出 · 架构决策（HLD）

> 项目：**Helios —— 分布式光伏与储能电站物联监控平台**
> 输入依据：`design/00-constraints.md` v1、`design/01-capability-map.md`
> 产出方式：`Plan` subagent（读文件路径，非粘贴内容），主线负责落盘
> 深度：概要设计。不含接口字段、表结构、代码、UI。不含图（Phase 3 单独出）。
> 说明：下文出现的分区数、保留期、keepalive、热层天数等均为**设计参数**（可辩驳、可调整），非新增业务指标；所有业务指标均可回溯到约束清单第 4/5/6 节。

## 0. 决策摘要（五条）

1. **拆分为 19 个部署单元**（14 个自研微服务 + 1 个边缘运行时 + 4 个中间件形态单元），按 3 个研发小组的 ownership 切分，8 个能力域全部有唯一归属，无兜底分类。
2. **选型**：MQTT Broker = EMQX 企业版自建于 ACK；时序库 = Apache IoTDB 自建集群 + OSS 冷层；流处理 = Apache Flink（优先阿里云全托管版）。被否备选与否掉理由见第 2 节。
3. **削峰的核心不是建 30 倍资源，而是分流**。50,000 msg/s 的主体是召测波形/高频数据，其归宿是 OSS，不是时序库。结论：**broker + Kafka 必须按峰值硬建**（连接数恒定，只是速率涨 30 倍）；**TSDB / 聚合 / 报表 / OSS 上传按稳态建 + 队列摊平**。
4. **告警与遥测的 Kafka 必须物理隔离（双集群）**；并且**边缘网关维持跨 AZ 双活 MQTT 连接**。这是同时满足"单 AZ 故障不中断"与"告警 P99 < 10s"的唯一低成本组合——单连接 + 快速切换方案在数学上无法同时达标（见 4.1）。
5. **量化估算推翻了能力清单问题 3 的前提**：最大单项存储成本是录波文件的 OSS（约 2.1 PB / 13 个月，≈ ¥11.4 万/月），不是时序库容量。时序库的成本由**写入峰值驱动的计算节点数**决定，削峰分流可年省 ¥45–115 万（见 3.2）。

## 1. 服务拆分方案

### 1.1 划分依据（四条，按优先级）

1. **故障域与 SLA 不同者必拆**：99.95%（接入+告警）、99.9%（查询+报表）、99%（OTA）三档 SLA 不得共存于一个部署单元，否则低档负载的故障与发布会吃掉高档 SLA 的预算。
2. **弹性特性不同者必拆**：无状态可水平扩（写入、通知分发）与有状态需 keyed 分区（流式聚合）不能同作业，否则扩容互相牵制。
3. **发布节奏与运行环境不同者必拆**：边缘（客户现场、不可随时升级、硬件异构）与云侧（ACK、周级发布）必须独立。
4. **18 人 3 组的可维护性上限**：人均负责 ~1 个服务单元。因此**不为"整洁"而拆**，薄逻辑合并进邻近服务（见 1.3 的合并取舍）。

### 1.3 命名规则与降级合并路径

- 命名规则：统一 `helios-` 前缀 + kebab-case + 名词化职责，禁用缩写歧义词（如 `-core`、`-common`、`-misc`）。**服务名一经冻结不得更改**——Kafka topic、监控项、审计记录、IAM 应用注册都引用它。Kafka topic 命名同构：`helios.<域>.<语义>`（见 2.4）。
- 若人力不足的降级合并顺序（按风险从低到高）：① `report-service` 并入 `query-service`（需接受批处理抢占在线查询的风险，用资源配额兜底）；② `thing-model` 并入 `asset-registry`；③ `observability` 退化为纯配置（不自研代码）。**不建议合并** `notify-dispatcher` 与 `tsdb-writer`——前者直接绑定 P99 < 10s，后者直接绑定峰值削峰。

## 2. 关键中间件选型

### 2.1 MQTT Broker：**EMQX 企业版，自建于 ACK `pool-connect`**

**为什么**：① 本项目峰值的特征是**连接数恒定（50 万）、消息速率涨 30 倍**，即 broker 的瓶颈是 CPU/网络而非连接表——自建集群可以按消息速率维度精确扩容，而托管服务通常按"连接数 × TPS"打包规格计费，为峰值 TPS 买单会连带买下一个远高于需要的连接规格。② 设备身份要求"一机一密 + X.509 双轨 + **在线轮换与吊销**"，需要自建 CA 链、可插拔认证钩子、以及 broker 侧对吊销名单的低延迟校验；托管 broker 的认证扩展点是黑盒或受限。③ 削峰需要在 broker 侧做 **topic 级/client 级限流与召测准入**（见 3.1），必须可编排。④ 边缘侧不需要 broker：逆变器/电表/PCS 走 Modbus TCP 与 IEC 104，**网关是唯一的 MQTT 客户端**——这一条把边缘的部署形态简化为单进程，显著降低异构适配面。

**被否备选**：
- **阿里云消息队列 MQTT 版（托管）**：与 Kafka 原生打通、免运维，是次优解。否掉的具体理由：(a) 50 万长连接 + 50,000 msg/s 峰值需长期持有高档规格，而峰值每年只出现少数小时（故障后召测），按峰值买断规格不经济；(b) 客户端证书吊销与自定义认证链的表达能力受限，一机一密降级路径难以自持；(c) broker 侧限流与准入不可编排，削峰只能后移到 Kafka，失去源头控制。**若 EMQX 自建 TCO 询价高于托管报价 20% 以上，此决策应重议**（列为待拍板 #6）。
- **VerneMQ / Mosquitto 集群**：Mosquitto 单线程模型无法在单节点承载 50 万连接的峰值消息速率，需要数十节点，跨节点桥接的一致性与会话管理自研成本高于收益；VerneMQ 具备集群能力但在 X.509 大规模轮换、规则引擎、Kafka 桥接的成熟度上需要自研补齐，18 人团队无法承担。
- **HiveMQ**：能力对标 EMQX，商业授权成本更高，且国内交付/支持半径与 ARM64 生态适配资料更少；无相对优势。
- **自研 broker**：直接否。长连接的会话管理、QoS 状态机、跨 AZ 集群一致性是被反复验证过的难题，自研会把 3 年 50 万站的进度押在未验证组件上。

### 2.2 时序库：**Apache IoTDB 自建集群（ACK `pool-data`）+ OSS 作为冷层**

**为什么**：① **模型契合**：IoTDB 的树形元数据模型（`root.helios.<region>.<station>.<device>.<point>`）与能力域 3 的"电站-设备-点位三级拓扑"同构，2000 万序列的元数据管理是其设计目标区间，不需要额外的标签索引层。② **云边格式统一**：这是本项目最强的架构论点——边缘 72h 缓存可直接以 TsFile 段为落盘单元，恢复后**整文件上传、云侧 load 入库**，天然满足"断点续传 + 补传去重"，无需逐点重放，也不需要为边缘缓存自研一套编码。③ **Java 生态**：IoTDB 为 Java 实现，Session/JDBC 客户端与 Java 17 + Spring Boot 3.x 栈同构。④ **Apache 2.0 顶级项目**，无开源版/企业版功能阉割（多级存储、连续查询、降采样均在开源版）。⑤ 冷层直接落 OSS，与公司标准一致。

**被否备选**：
- **InfluxDB（1.x/2.x OSS）**：否。series cardinality 是硬伤——2000 万序列下 1.x/2.x 的内存索引会膨胀到数十 GB 量级且无法分片；2.x OSS 不具备可用的水平扩展，50 万站终态必须靠外部分片自研，等于自建一套分布式层。
- **阿里云 Lindorm 时序引擎（托管）**：**次优解，且是回退方案**。原生冷热分层到 OSS、有 SLA、免运维。否掉的具体理由：(a) 边缘无对应形态，云边存储格式不一致，72h 缓存必须自研编码 + 逐点补传，把"边缘自治"这一硬约束的实现复杂度显著抬高；(b) 峰值 2M 样本/s 需预购规格，与 (a) 叠加后总成本不一定低于自建；(c) 锁定。**触发回退的条件**：PoC 阶段 IoTDB 在 2000 万序列 + 2M 样本/s 写入下不达标，或数据层运维人力评估 < 2 人全职（列为待拍板 #5）。
- **TDengine**：超级表模型同样契合"一物一表"，压缩比与写入性能优秀。否掉的具体理由：(a) C 实现，与公司 Java 栈的排障/二次开发能力不匹配；(b) 多级存储等关键能力在开源版/企业版之间的边界需要逐一核验，存在功能被锁在企业版的风险；(c) 边缘轻量形态与云侧集群的同构性弱于 IoTDB 的 TsFile 方案。
- **TimescaleDB**：PostgreSQL 扩展，多租户与 SQL 亲和性好。否掉：2000 万序列 × 13 个月原始（约 2.3 万亿样本）的量级下，分区维护（chunk 数量）与压缩任务的运维复杂度、以及写入吞吐上限，都需要引入外部分片，得不偿失。
- **ClickHouse 自建**：列存压缩比极佳，适合做冷层查询。否掉作为主时序库：缺少时序原生的降采样/连续聚合/迟到数据处理语义，需要在其上自建一整套时序语义层。**保留为分钟级聚合 5 年冷层的可选查询加速引擎**（本期不建）。
- **VictoriaMetrics / Thanos + Prometheus**：标签模型与保留期模型不匹配"13 个月原始 + 5 年分钟聚合"的双层诉求，且面向指标而非设备测点，2000 万序列的租户隔离与物模型语义缺失。

### 2.3 流处理：**Apache Flink（优先阿里云全托管 Flink 版；成本敏感时自建 Flink on ACK）**

**为什么**：① 告警 P99 < 10s 需要**事件时间语义 + 模式匹配**（能力域 5 明确含"变化率/组合条件"），Flink CEP 是现成能力。② 峰值 50,000 msg/s 需要**秒级弹性且不中断处理**——Flink 的 rescale / Reactive Mode 与托管版的自动调优可在不触发全量重平衡的前提下扩容。③ 边缘 72h 补传意味着**数小时至 3 天前的数据会突然到达**，Flink 的 watermark 策略 + 侧输出 + savepoint 有界回补是处理迟到数据的标准手段。④ RocksDB 状态后端 + 增量 checkpoint 可承载 2000 万点位的窗口状态，checkpoint 落 OSS 与公司标准一致。

**被否备选**：
- **Kafka Streams**：否，三条具体理由：(a) **无模式匹配能力**，"组合条件告警"要各小组自研状态机，3 个小组的重复劳动与语义不一致风险；(b) **扩缩容触发 consumer group 全量 rebalance**，在 30 倍峰值来临的那一刻正好需要扩容，而扩容本身会造成秒级至分钟级的处理停顿——这与告警 SLA 直接冲突；(c) 跨 sink 的端到端一致性需自建两阶段提交，Flink 的连接器生态已覆盖。
- **Spark Structured Streaming**：否。微批模型在默认配置下的端到端延迟对 10s 预算的余量不足（continuous 模式成熟度与状态支持受限），且 CEP 与迟到数据处理能力弱于 Flink。
- **不用流处理，全部在应用服务内做**：否。分钟/小时/日多级聚合 + 2000 万点位的状态，用无状态微服务 + 定时任务实现会产生海量数据库扫描，且召测峰值下必然拖垮 MySQL。
- **托管 vs 自建的取舍**：托管版省去 JobManager HA、状态后端调优、版本升级；代价是长期费用与厂商锁定。**建议首年用托管版换取交付速度，阶段 3 视成本曲线评估自建**（可逆决策，列为待拍板 #7）。

## 3. 满足规模指标的关键设计手段

### 3.1 问题 1：稳态 1,700 msg/s vs 峰值 50,000 msg/s（30 倍）

**先给结论性判断：不是"建多少"的问题，而是"哪一层必须硬抗、哪一层可以摊平、哪一层根本不该收到这股流量"。**

按约束推算的量级（全部可回溯）：稳态 1,700 msg/s = 66,700 样本/s（× 40 点位）；峰值 50,000 msg/s = **2,000,000 样本/s**；首年 8 万站对应稳态 267 msg/s、按比例峰值 8,000 msg/s。

**分层结论**

| 层 | 是否随峰值 30 倍 | 建设策略 | 理由 |
|---|---|---|---|
| 长连接数（50 万） | **不变** | 按终态一次建成，跨 AZ 各 100% | 召测发生在既有连接上，不新增连接。这是本项目最重要的容量事实：接入层的压力是消息速率而非连接表 |
| broker CPU/网络 | 30 倍 | 常驻按稳态 + 30%，跨 AZ 各 100%，峰值靠池内余量吸收 | broker 只做协议卸载 + 鉴权 + 桥接 Kafka，立即卸载到 Kafka，不在本层堆积 |
| Kafka（遥测集群） | 30 倍 | **必须硬建**：约 200 MB/s 级写入（按 ≤4 KB/报文），3 副本 ≈ 600 MB/s 落盘，8–12 台 NVMe broker | Kafka 是唯一蓄水池，堆积能力 = 磁盘容量，允许 lag 涨到千万级而不丢数据 |
| TSDB 写入 | **≈1.5 倍，不是 30 倍** | 按稳态 66,700 样本/s + 50% 余量建（3–6 个数据节点 × 3 副本） | 见下"分流" |
| Flink 聚合 | ≈1.5 倍 | KEDA 按 lag 弹性扩容，按量付费节点组，仅召测窗口拉起 | 常态成本按稳态，峰值成本按小时计 |
| OSS 上传（录波） | 30 倍 | 边缘队列 + 分片并发上限 + 可摊平到小时级 | OSS 本身弹性无限，瓶颈在边缘上行带宽与凭证签发速率 |
| 报表/查询 | 不变 | 按 99.9% 档建设，峰值期主动降级 | 低 SLA 层为高 SLA 层让路 |

**六项具体机制**

1. **分流（贡献最大）**：召测拉取的录波/高频波形**不进时序库**。波形文件由边缘分片直传 OSS，Kafka 只承载文件元数据与上传完成事件；时序库只写入召测窗口的**摘要特征值**（例如故障区间的有效值/极值/越限时刻）。这一刀把 TSDB 的峰值写入从 2,000,000 样本/s 压回 ≈100,000 样本/s，节点数与费用降约一个数量级。**推论：时序库根本不需要按峰值建设**，"按峰值建常态资源极度浪费"的困境在这一层被消解。
2. **源头准入（可调度部分）**：召测由平台发起，因此**部分峰值是可调度量**。`helios-edge-manager` 内的召测调度器维护持久化任务队列 + 令牌桶，按数据链路水位（Kafka lag、TSDB 写入队列深度、OSS 上传在途数）反馈动态调节在途召测站数；**故障驱动的召测优先级最高且不受令牌限制**，巡检类召测可被抢占与延后。诚实说明：电网故障后的批量召测（如区域性灾害）**不可调度**，因此第 1、3、4 条机制必须独立成立，准入只用于摊平非故障流量。
3. **边缘整形（复用自治能力，零新增资源）**：召测指令携带云端下发的 `rate_budget`，网关按预算分片上报，超出部分留在本地磁盘队列。**72h 自治缓存因此同时是削峰的第一级缓冲**——这是把硬约束转化为容量红利。
4. **接口硬约束**：MQTT 单报文 ≤ 64 KB，超限必须切块或改走 OSS 直传。理由可量化：若按 11 MB/站/日 反推单报文体积（11 MB ÷ 288 ≈ 38 KB），50,000 msg/s 将产生 **1.9 GB/s** 的 Kafka 写入，任何合理集群都无法承受且 24h 保留需 PB 级磁盘。因此"文件不入 Kafka + 报文体限长"不是优化项而是可行性前提。
5. **配额与优先级**：Kafka client 级 byte-rate 配额隔离召测流量与常规遥测；消费侧三档优先级——告警 > 常规遥测 > 召测/补传。峰值期若 lag 超阈值，接入层对低优先级召测返回 MQTT 5.0 `Server Busy` 并停止发新令牌（**背压回推到源头，而不是在云端丢弃**）。
6. **降级矩阵（预先约定，不临场决策）**：峰值/故障期自动暂停 OTA（约束允许 99%、可暂停）释放边缘上行带宽与云侧资源；遥测查询降级为"仅热层 + 限制时间范围 + 强制返回预聚合"；报表延后；冷层回捞任务全部暂停。

### 3.2 问题 3：2000 万点位 × 13 个月原始 + 5 年分钟聚合的冷热分层与成本

**分层方案（四层）**

| 层 | 内容 | 介质 | 保留 | 访问路径 |
|---|---|---|---|---|
| L1 热 | 近 90 天原始遥测（压缩后 1.6–5.2 TB） | IoTDB 数据节点本地 ESSD/NVMe | 90 天 | `query-service` 同步查询，承载 **P99 < 2s** |
| L2 温 | 91 天–13 个月原始 | IoTDB TsFile 分级存储指向 OSS（标准/低频） | 至 13 个月 | 同步查询但允许更慢；**明确不受 P99 < 2s 约束**（约束只要求"单站 30 天历史曲线"） |
| L3 冷 | 5 年分钟级聚合（列存，10.5 万亿样本量级） | OSS 归档/冷归档 | 5 年 | **异步任务 + 结果落 OSS + 通知**，不进在线查询 SLA |
| L4 文件 | 录波等二进制（约 5.5 TB/日） | OSS：近 90 天标准 → 91–395 天归档 | 13 个月 | `file-service` 元数据索引 + 预签名 URL |

**P99 < 2s 的达成机制**（不是靠堆硬件）：单站 30 天 = 40 点位 × 288 × 30 ≈ 34.6 万原始样本，而前端曲线只需约 1,000 个像素点。因此查询必须**把降采样下推到存储层**（按 30 分钟粒度聚合，返回 1,440 行 × 40 点位），并在 Redis 缓存降采样结果（大屏轮询命中率高）。L1 全在本地 SSD，扫描量下降两个数量级后 2s 有充分余量。

**量化成本估算**（阿里云华东 1 公开价目**量级**估算，非报价；单价取值：OSS 标准 ¥0.12/GB·月、归档 ¥0.033、冷归档 ¥0.015；ESSD ¥1/GB·月；8C32G 云主机 ¥3,000–5,000/月量级）

| 项 | 量级（50 万站终态） | 月成本量级 |
|---|---|---|
| 遥测原始 13 个月（3–10 B/样本压缩） | 6.8–22.8 TB（2.28 万亿样本） | L1 ESSD ¥1.6k–5.2k；L2 OSS 归档 ¥200–700 |
| 分钟级聚合 5 年（1–2 B/样本列存） | 10.5–21 TB（10.5 万亿样本） | OSS 归档/冷归档 ¥350–700 |
| **录波等文件 13 个月** | **≈2.1 PB**（5.5 TB/日 × 395 日） | 近 90 天标准 495 TB ≈ **¥6.1 万**；其余 1.6 PB 归档 ≈ **¥5.7 万**；合计 **≈¥11.8 万** |
| 审计日志 3 年 WORM | < 10 TB | < ¥1.2k |
| **存储小计** | | **≈¥12 万/月 ≈ ¥145 万/年** |
| 对照：全量放标准存储不分层 | 2.1 PB | ≈¥26.7 万/月 → **分层节省约 55%** |
| TSDB 计算节点（**由写入峰值驱动**） | 若 2M 样本/s 全量入库：12–30 个 8C32G 数据节点 | ¥5–12 万/月 |
| 同上，采用 3.1 的分流后 | 峰值 ≈10 万样本/s：3–6 节点 | ¥1.2–2.5 万/月 → **年省 ¥45–115 万** |
| Kafka（遥测集群 8–12 台 NVMe，24h/6h/3h 分级保留） | 峰值 200 MB/s、常态 6.8 MB/s | ¥3–6 万/月量级 |
| 首年 8 万站（按 0.16 比例线性折算） | | 存储 ≈¥2 万/月量级 |

**结论与对前提的挑战**：能力清单问题 3 假设"时序库选型与冷热分层的成本曲线是本项目最大的单项成本"。**按约束给定的 11 MB/站/日 推算，这个前提不成立**：时序数据 13 个月压缩后仅 7–23 TB（因为 40 点位 × 5 分钟的样本量本就不大），而文件类数据是 2.1 PB，两者相差约两个数量级。真正的成本大头是 (a) 录波文件的 OSS 分层策略、(b) 由写入峰值驱动的 TSDB/Kafka 计算规格。因此架构上的成本杠杆是**生命周期分层 + 峰值分流**，而不是换一个压缩比更高的时序库。

**估算的前提敏感性（必须声明）**：11 MB/站/日 中"文件 vs 结构化遥测"的占比、以及单条整站报文内是否携带秒级子采样，约束清单未给定。若报文含秒级子采样（每报文 40 点 × 60 秒级值 ≈ 38 KB 恰好吻合），全网样本量将放大约 60 倍（至 345 G 样本/日、4M 样本/s 稳态写入），TSDB 侧成本上升 1–2 个数量级、OSS 侧相应下降，**整个成本结构与写入架构都要重算**。这是待拍板 #2，在业务方确认前，上述数字只能作为量级判断而非预算依据。

## 4. 满足可用性与合规目标的具体机制

### 4.1 99.95%（接入 + 告警）、单 AZ 故障不中断

99.95% ⇒ 月度不可用 ≤ **21.6 分钟**。以下是机制，不是"多副本"口号。

**核心矛盾与其解法**：若边缘只维持单条 MQTT 连接，AZ 故障后网关需经历"keepalive 超时判定（1.5 × keepalive，即使 keepalive = 15s 也需 22.5s）→ 端点切换 → TLS 重握手"。这段时间内该站告警无法上行。AZ 故障影响约 50% 站点，**P99 必然被击穿**（P99 是统计量，50% 样本受影响时 P99 就等于故障期时延）。

**决策：边缘网关维持跨 AZ 双活 MQTT 连接**
- 网关同时持有两个 broker 端点（两组跨 AZ 的 NLB VIP）并**同时建立两条连接**；告警在两条连接上**双发（QoS 1）**，云侧按 `(stationId, alarmSeq)` 幂等去重；遥测只走主连接（避免双倍上行带宽与云端双倍写入），主连接健康探测失败后 < 1s 切到备用连接。
- 故障检测：主连接上的应用层轻量探测周期 5s，连续 2 次失败即判定 → 检测 < 10s，切换 < 1s，告警中断窗口可控制在 SLA 预算内。
- 代价（必须写进容量模型）：**broker 集群的连接数从 50 万变为 100 万**，节点数由连接数而非消息速率驱动；边缘侧 2C4G 承载 2 条 MQTT 连接的内存/CPU 开销可忽略；带宽增量仅为心跳（全网约 2 × 33,000 PINGREQ/s，报文极小）。
- 被否的选项（单连接 + 端点级快速切换 + 端点内重试抖动）：成本更低（连接数不翻倍），但如上所述无法满足 P99 < 10s，仅在业务方接受"AZ 故障期间告警时延放宽到 60s"时才可选（待拍板 #3）。

**重连风暴的量化处理**：AZ 失效后 50 万连接会在存活 AZ 重建。若抖动窗口 30s ⇒ 16,700 conn/s；TLS 握手在 8C 节点上约 5,000–10,000 次/s（含证书链校验与鉴权回调），故存活 AZ 需 ≥ 4 节点的握手能力——这正好被"每 AZ 常驻 100% 容量"的冗余要求覆盖。缓解叠加：网关侧重连退避带随机抖动（0–30s）、broker 侧新连接速率限制（保护鉴权服务与 MySQL/Redis 不被打穿）、TLS session resumption 降低握手成本、鉴权结果短 TTL 缓存。

**其余各层的具体机制**
- broker：每 AZ ≥ 2 节点、集群 ≥ 4 节点，**单 AZ 失效后另一 AZ 可承载全部 100 万连接 + 峰值消息速率**（即 2× 容量成本，这是"单 AZ 不中断"的真实价格，须在预算中明示）。
- Kafka：3 副本跨 AZ + rack awareness + `min.insync.replicas=2`；告警集群 `acks=all`，遥测集群 `acks=1`（配合边缘 QoS 1 + 云端幂等，不追求 broker 侧强持久，换取峰值吞吐）。
- IoTDB：副本组 3 副本跨 AZ、写入 quorum = 2，单 AZ 失效仍可写；L2/L3 数据在 OSS 天然跨 AZ 冗余。
- Flink：JobManager HA（K8s）+ checkpoint 落 OSS；**告警作业刻意做成近无状态**（去重/抑制状态外置 Redis），AZ 切换只需重启 task，恢复 < 30–60s。
- MySQL RDS 高可用版跨 AZ 主备（切换 < 30s）+ 只读实例；Redis 集群版跨 AZ 主从。
- 外部依赖隔离：公司告警中心 Webhook / 短信 / App 推送网关均为外部系统，`notify-dispatcher` 对三者各配独立线程池 + 独立熔断器 + 持久化重试队列（MySQL），任一通道故障不阻塞其余两路。
- **SLA 语义边界（必须澄清）**：约束同时要求"99.95% 告警可用"与"云侧完全中断时边缘自治"。云侧全断期间，边缘本地告警逻辑可继续运行，但**通知无法送达用户 App**（除非现场有本地声光/干接点/本地 H5）。因此本方案定义：99.95% 的分母**排除"云侧完全中断"这一灾难场景**；边缘自治保证的是"数据不丢 + 本地判定不停 + 恢复后补传"，不保证"通知送达"。此语义需业务方书面确认（待拍板 #3）。

### 4.2 问题 2：边缘自治是硬约束 —— 对能力边界与云边协议的要求

**结论：边缘网关不是薄客户端，而是一个"具备完整采集-判定-存储-补传能力、可离线运行 72 小时的微型数据平台"，云侧是它的配置源、聚合层与最终一致性的收敛点。**

**能力边界（边缘必须具备的 8 项）**
1. **物模型的本地已签名快照**：点位映射、量纲换算、缩放系数必须能在离线 72h 内按最后已知版本正确解析；快照带版本号与签名，恢复后与云端做一致性校验。要求物模型**强制版本化且向后兼容**。
2. **本地规则引擎 + 资源预算约束**：规则集由云端编译为边缘可执行形态并做资源校验（建议上限：单站规则数 ≤ 200、表达式不含跨站聚合、不含需要长历史窗口的统计）。**能力分工必须写死**：单站/单点/短窗口的阈值、变化率、组合条件 → 边缘；跨站关联、需长历史、需全网视图的规则 → 云侧 `alarm-engine`。这决定了能力域 2 与域 5 的边界。
3. **分级环形缓存**：72h 缓存按约束的 11 MB/站/日 仅需 ≈33 MB，容量不是瓶颈；**真正的瓶颈是断网期间的故障录波**（单次可达数十 MB）。因此缓存必须分级并定义淘汰优先级：告警事件与关键遥测 > 常规遥测 > 录波文件；空间不足时按优先级淘汰，且**淘汰必须留痕**（写入本地日志并上报），否则"数据完整率"指标会失真。另需注意 flash 写寿命：33 MB/日环形写 + wear leveling，3 年累计写入约 12 GB，普通 eMMC 可承受，但必须禁用无节制的高频落盘。
4. **块级幂等补传单元**：按固定窗口（5 分钟）打包为数据块，块头含 `(stationId, blockSeq, blockHash, windowStart, windowEnd, schemaVersion)`；云侧按 `(stationId, blockSeq)` 去重（Redis 幂等键 + TSDB 写入去重）。**块级而非消息级重传**，避免 72h 补传时产生数亿条独立消息的重放风暴。
5. **本地时钟与偏移记录**：数据块时间戳使用**采集时刻**；网关持续记录云端下发的参考时间与本地时钟偏移，补传时按偏移修正。断网期间时钟漂移不可避免，因此云端必须能识别"时间戳可疑"的块并单独标记。
6. **补传流量与实时流量分离**：补传块走独立 topic `helios.block.late`，由独立的批处理消费者处理。**架构决策：补传数据不进流式链路**——若用 Flink 的 allowedLateness 承载 72h 迟到，窗口状态会膨胀到不可运维。正确做法是写入 TSDB 后，由有界流批作业重算受影响时间窗的分钟/小时/日聚合。
7. **补传告警的抑制**：补传数据不得触发历史告警风暴（72h 的告警一次性涌入会淹没用户）。块标记 `lateArrival=true` 后，告警服务对其**只入库与统计、不实时通知**，并按抑制策略合并为一条"离线期间告警汇总"。此为产品语义决策，需业务方确认（待拍板 #3 附带项）。
8. **双活连接与本地 OTA 安全**：见 4.1；OTA 采用 A/B 双分区 + 签名校验 + 失败自动回滚，断网时不下发、恢复后续传，且**OTA 任务在峰值/故障期自动暂停**。

**云边协议要求（清单）**
- **以 MQTT 5.0 为主路径，3.1.1 为兼容降级路径**。选 5.0 的具体理由：User Properties 携带 `blockSeq/traceId/schemaVersion`（不侵入 payload）、Reason Code 支持 `Server Busy` 做端到端背压、Topic Alias 降低 50 万连接高频报文的头部开销、Shared Subscription 做云侧消费均衡、Session Expiry 精确控制离线会话。但能力清单要求同时支持 3.1.1，故**payload 必须自包含**，不得依赖 5.0 独有特性，否则 3.1.1 站点无法补传与去重。
- **QoS 语义**：遥测 QoS 1 + 云端幂等去重；告警 QoS 1 + 双活连接双发；下行指令 QoS 1 + 应用层 ACK + 全量审计。**不使用 QoS 2**——其四次握手的吞吐与状态成本在 50,000 msg/s 峰值下不划算，幂等在应用层用块序号实现更简单可靠。
- **会话责任划分**：72h 自治的责任在边缘，不在 broker。broker 侧 Session Expiry 设短（10 分钟量级，仅用于平滑重连），**绝不为 50 万连接保存 72h 离线消息**——否则 broker 会变成存储系统并被峰值击穿。keepalive 15s（配合双活探测）。
- **Topic 命名规范（稳定、自解释、支持通配订阅）**：上行 `helios/{env}/up/{region}/{stationId}/{telemetry|alarm|block|file-meta|health}`；下行 `helios/{env}/dn/{stationId}/{cmd|config|rules|ota|cert|recall}`。命名冻结后不得变更（边缘固件升级周期长，向后兼容成本极高）。
- **文件通道**：录波文件不经 MQTT。网关通过下行 `file-meta` 申请 STS 临时凭证，向 OSS 分片直传，完成后上报元数据事件。凭证按站按文件最小权限、有效期 ≤ 15 分钟。
- **证书在线轮换与吊销的规模化**：自建 CA 层级（离线 Root → 中间 CA → 设备证书）；设备证书**短有效期（建议 90 天）** + 到期前 30 天窗口自动续签，续签时新旧证书并存（grace period）避免轮换期断连；**到期时间必须随机打散**——50 万证书 / 90 天 ≈ 5,600 次/日续签（量很小），但若按批次集中到期会形成握手风暴并与重连风暴叠加；吊销采用 OCSP + broker 侧吊销名单短 TTL 缓存（Redis），**不采用全量 CRL 分发**（50 万条目的 CRL 体积与解析成本在每次连接时都不可接受）；中间 CA 轮换需有预案与演练。
- **边缘硬件异构**：边缘运行时需提供统一的硬件抽象层（串口/网口/存储/看门狗/RTC），并对每种现场硬件型号建立适配矩阵与出厂预置镜像，禁止现场手工配置。

### 4.3 问题 4：告警链路能否与遥测链路共用同一条 Kafka 通道

**结论：不能共用集群，必须物理隔离——建两个 Kafka 集群（`helios-kafka-telemetry` / `helios-kafka-alarm`）。**

**理由（四条，可辩驳）**
1. **SLA 与负载形态根本不同**：遥测集群是"大磁盘、高吞吐、允许堆积、保留 6–24h、acks=1"；告警集群是"小磁盘、低吞吐、零堆积容忍、保留 7d、acks=all + min.insync.replicas=2"。同一集群无法同时最优。
2. **峰值期的资源争用是真实机制而非假想**：召测峰值下遥测 topic 以约 200 MB/s 写入并允许 lag 涨到千万级，broker 的磁盘 IO 与 **page cache** 会被顺序大流量占满；告警消息的消费端读会退化为磁盘读，端到端时延从亚秒级恶化到秒级——这直接吃掉 10s 预算中给 Kafka 的 0.3s 份额。Kafka 的 quota 只能限客户端速率，**无法隔离 page cache 与磁盘调度**，所以"同集群 + 独立 topic + 配额"不足以满足 99.95%。
3. **故障域与可用性目标绑定关系**：约束把 99.95% 绑定在"设备接入 + 告警"，遥测查询只有 99.9%。共用集群等于把两条不同 SLA 的链路绑进同一故障域，与约束的分级意图矛盾。
4. **成本可忽略**：稳态告警量远小于遥测量（告警是事件，遥测是周期采样），告警集群 3–5 台小规格 broker 即可，增量成本在整体中占比很低（个位数百分比）。

**被否的折中方案**
- **方案 A：单集群 + 告警独立 topic + 配额 + broker 分组（rack）**。成本最低，但如上第 2 条，page cache 与磁盘调度层面的干扰无法通过配额消除；且集群级故障（元数据控制器、版本升级失误）同时击穿两条链路。仅在预算被硬性压缩且业务方接受告警 P99 放宽时可选。
- **方案 C：告警完全绕过 Kafka**（broker 规则引擎直推告警服务）。时延最低，但失去削峰与重放能力，且 broker 侧规则引擎的表达能力弱于 Flink CEP。**可作为可选的旁路加速通道**：一级告警双发（主链走 Kafka + Flink，旁路由 broker 直推），云侧去重。**本期不建，留作阶段 3 的优化选项**。

**告警链路的结构与 P99 < 10s 时延预算**

两条入口：边缘已判定的告警走 `helios.alarm.edge` → `alarm-service` 快路径（**不经 Flink**，跳数最少）；云端规则产生的告警走 `alarm-engine`（Flink CEP）→ `helios.alarm.fired` → `alarm-service`。之后统一由 `notify-dispatcher` **并行**推 App / 短信 / 公司告警中心 Webhook。

| 环节 | P99 预算 |
|---|---|
| 边缘判定 + 4G/5G 上行（QoS 1，双活连接） | 2.0s |
| broker 鉴权/路由 → Kafka produce（acks=all，3 副本跨 AZ） | 0.3s |
| `alarm-service` 消费 + 去重/抑制/分级（Redis） | 0.5s |
| 三通道**并行**分发（各自超时 2s、失败重试 1 次、独立熔断） | 3.0s |
| **余量** | **4.2s** |

**告警风暴抑制是达成 P99 的前置条件**：召测峰值通常伴随故障，告警量会激增，若无抑制（同站同点位 N 分钟合并、区域级故障收敛为父告警 + 子告警折叠、按租户的通知限流并转汇总），`notify-dispatcher` 会被淹而击穿时延。**待澄清**：P99 < 10s 的度量终点是"到达用户设备"还是"成功提交给推送网关"，以及三通道是否都需满足 10s——短信通道在运营商侧不可控，若按"到达"计则该 SLA 无法承诺（待拍板 #3）。

### 4.4 等保三级与电力行业合规（Ⅲ 区、只监视不控制）对架构分区的要求

**网络与分区**
1. VPC 内四个子网区：**DMZ 区**（`openapi-gateway`、broker 接入 VIP、WAF 之后）、**应用区**（全部微服务与 Flink）、**数据区**（MySQL/Redis/Kafka/IoTDB，**无公网入口**，仅安全组内白名单可达）、**边缘接入区**（专线/VPN 网关落地）。跨区流量强制安全组 + NACL 白名单，数据区禁止任何北向发起的连接。
2. **纵向认证**：边缘到平台强制 X.509 双向 TLS（一机一密仅作初始注册与降级通道）；专线客户经 VPN 网关/智能接入网关加密落地。
3. **横向隔离的责任边界（关键合规约束）**：本平台位于管理信息大区（Ⅲ 区），不直接控制电网侧设备。由此推出一条必须写进设计与合同前置条件的硬约束：**边缘网关不得同时连接 Ⅰ/Ⅱ 区设备与云平台**，否则网关本身构成跨区通道，违反横向隔离。客户 SCADA/EMS 若位于 Ⅱ 区，须由**客户侧**在 Ⅱ/Ⅲ 区之间部署正向/反向隔离装置，网关只接 Ⅲ 区侧。平台侧不提供任何通往 Ⅰ/Ⅱ 区的通道。此项为交付前置依赖，未落实不得接入（待拍板 #4）。
4. **"只监视不控制"必须在协议层可验证**，而不只是文档声明：边缘运行时的 Modbus 适配**只实现只读功能码（0x03/0x04），固件层面不实现写单/多寄存器（0x05/0x06/0x10）**；IEC 104 侧不实现遥控/遥调 ASDU。下行指令类型枚举中不存在任何一次设备控制项，且 `edge-manager` 与 `audit-service` 双重白名单校验。这样"平台不可能控制电网侧设备"变成一个**可审计、可代码验证**的事实。平台下行仅限自身管理面：网关远程重启、采集参数下发、规则集/配置下发、OTA、召测。

**等保三级映射（架构层面的落点）**
- 身份鉴别：接入公司统一 IAM，不自建账号体系；运维入口强制双因素。
- 访问控制：`helios-access-control` 作为统一 PDP，RBAC + 多租户（业主/运维商/EPC）+ **电站级数据范围**，所有服务的数据访问必须经 PDP 决策，禁止服务内自行判断权限。
- 安全审计：`helios-audit-service` 全量记录下行指令，写 OSS 合规保留（WORM）≥ 3 年，**系统管理员无删除权限**；实行三权分立（系统/安全/审计管理员），审计日志仅审计管理员可读。
- 数据保密性与完整性：全链路 TLS；存储加密（RDS TDE、OSS SSE-KMS、IoTDB 落盘加密、Kafka 磁盘加密）；数据块带 `blockHash` 校验完整性。
- 入侵防范与恶意代码防范：WAF + 云防火墙 + 主机安全 + 容器镜像签名与扫描（CI 门禁）+ 边缘固件签名与 A/B 回滚。
- 备份与恢复：RDS/IoTDB/Redis 跨 AZ 备份，**每季度恢复演练并留记录**（等保测评必查项）。
- 数据不出境：单 Region 华东 1，全部存储境内；**必须关闭所有开源组件与 SDK 的对外遥测/统计上报**（EMQX、Flink、IoTDB、各类 agent），这是实际项目中最容易漏的一条。

| R9 | **合规边界模糊** | 客户未在 Ⅱ/Ⅲ 区之间部署隔离装置；北向数据输出被解读为向 Ⅱ 区提供通道；下行指令范围被逐步扩大到含控制语义 | 无法通过等保测评/电力安全检查，项目停摆 | 交付前置条件写入合同与验收清单；架构层面不提供通往 Ⅰ/Ⅱ 区的通道；下行指令白名单 + Modbus 只读功能码硬约束 + 全量审计；范围变更须经合规评审 |
| R10 | **交付能力与服务粒度失衡**（实施风险） | 19 个部署单元对 18 人 3 组；跨组接口联调滞后 | 阶段 1/2 里程碑延误，质量下降 | 第 1 节给出降级合并路径；服务名与 topic 名在阶段 0 冻结并出命名表；每组对自己域内的服务端到端负责（含 SLO 与 on-call）；跨组接口以契约测试先行 |
| R11 | **分区与序列设计造成热点** | 区域故障时同区域站点集中于少数 Kafka 分区；召测数据倾斜 | 局部 lag 堆积、消费不均衡、P99 恶化 | 分区键用 `stationId` 哈希均匀分布（不用 region 作键）；分区数一次设到终态（128）；上线前用真实站点分布做倾斜度压测 |
| R12 | **单 Region 双 AZ 的天花板** | Region 级故障（约束第 8 节明确本期不做跨 Region 容灾） | 全网监控与告警完全失效 | 明确书面告知业务方并由其接受风险；边缘自治保证数据不丢与本地判定不停；把"跨 Region 容灾"作为下期范围显式登记 |
| R13 | **容量演进不可逆** | Kafka 分区只能扩不能缩；序列基数与物模型设计定型后改造成本高 | 三年演进中被早期决策锁死 | 分区数、序列键、topic 命名、物模型版本策略在阶段 0 按**终态 50 万站**设计，只有计算与存储资源按阶段扩容 |

## 6. 分阶段实施建议

> 装机节奏来自约束：首年 8 万座、三年 50 万座。**中间年份的装机数约束未给定，因此各阶段的容量验收一律以"终态指标压测达标"表达，不引入新的装机指标。** 首年对应的峰值按 8 万/50 万 = 0.16 比例推算为 8,000 msg/s（推算值，非约束指标）。

| 阶段 | 时间 | 范围 | **可度量验收标准** | 不达标时的动作 |
|---|---|---|---|---|
| **阶段 0 · 技术验证与地基** | M0–M2 | 三项自选中间件 PoC；服务名/topic 名/物模型版本策略冻结；网络与安全分区落地；边缘硬件白名单与首批型号适配；CA 层级建立 | ① EMQX：单 AZ 承载 25 万连接 + 25,000 msg/s 持续 30 min，broker 内部转发 P99 < 200ms，零丢失；kill 一个 AZ 后另一 AZ 在 5 min 内承载全部连接，新建连接速率 ≥ 16,700 conn/s 不触发鉴权服务过载。② IoTDB：2000 万序列建模完成，写入 **2,000,000 样本/s 持续 10 min** 无积压，单站 30 天曲线（降采样下推）在 100 并发下 **P99 < 2s**，冷层从 OSS 读取可用。③ Flink：告警从 Kafka 入口到通知提交 **P99 < 3s**，规则热更新不中断作业，AZ 故障后作业恢复 < 60s。④ 边缘：断网 72h 后补传，**数据完整率 ≥ 99.9%、重复块为 0**。⑤ 命名表评审通过并冻结 | 任一项不达标即触发选型回退（IoTDB → Lindorm；EMQX → 托管 MQTT），并重跑本阶段，**不得带未验证组件进入阶段 1** |
| **阶段 1 · 核心链路 MVP（试点）** | M2–M6 | 域 1/2/3/4 主链 + 域 5 单通道告警 + 域 6 审计；Kafka 双集群；L1 热层 | 试点电站连续 **30 天**真实运行：接入 + 告警链路可用性 **≥ 99.95%**（月度不可用 ≤ 21.6 min）；告警端到端 **P99 < 10s**（样本 ≥ 1,000 条）；遥测查询（单站 30 天）**P99 < 2s**；数据完整率 **≥ 99.5%**；边缘自治演练 **≥ 3 次、每次 ≥ 4h 断网，零数据丢失、零重复**；下行指令审计覆盖率 **100%**（抽样 500 条比对） | 未达标则冻结功能扩张，专项修复后重跑 30 天窗口 |
| **阶段 2 · 首年规模化（8 万座）+ 削峰与三通道** | M6–M10 | 域 4 全量、域 5 全量（CEP + 三通道 + 去重抑制闭环）、域 7、域 8、域 6（在线率/完整率/成本水位） | ① 8 万座接入并稳定运行 30 天，接入 + 告警可用性 **≥ 99.95%**。② **峰值压测：8,000 msg/s 持续 1 小时**，期间告警 P99 仍 **< 10s**、常规遥测**零丢弃**、Kafka lag 在压测结束后 30 min 内收敛。③ **单 AZ 故障演练**：kill 一个 AZ 全部 broker 与应用节点，接入与告警中断 **< 5 min**，双活连接切换成功率 ≥ 99%。④ 冷热分层实测：**存储月成本实测 ≤ 预算 ±20%**。⑤ 三通道并行分发：任一通道故障注入时其余两通道 P99 劣化 > 10% 即判失败。⑥ 遥测查询 P99 < 2s 在 8 万座负载下复测通过 | 削峰未达标则回退到"限制在途召测站数"的保守令牌参数，并把 R1 升级为项目级风险；成本超预算 20% 则触发保留策略与分层参数复审 |
| **阶段 3 · 终态能力验证与成本效率** | M10–M24 | 容量按终态扩展；边缘异构扩展（≥ 3 种硬件型号）；证书全量轮换演练；5 年分钟聚合层与数据回捞验证；成本优化；Flink 托管 vs 自建 TCO 复评 | ① **终态压测达标**：在 50 万座 / 稳态 1,700 msg/s / **峰值 50,000 msg/s** 的压测模型下，告警 P99 < 10s、遥测零丢弃、TSDB 写入不积压（即使实际装机未到终态，架构能力必须先验证）。② **50 万证书完成一轮在线轮换，零非预期断连**，续签成功率 ≥ 99.9%。③ 边缘白名单型号 ≥ 3，每型号通过 72h 自治验收。④ 分钟级聚合 5 年层可查询（异步任务 30 min 内返回 1 年跨度结果）。⑤ 单站年均成本较阶段 2 下降 ≥ 15%。⑥ 数据回捞演练成功率 100% | 终态压测不达标则定位瓶颈层并做专项扩容/重构，**不得以"实际装机还没到"为由跳过** |
| **阶段 4 · 满负荷运营** | M24–M36 | 50 万座满负荷运行；稳态运营、SLO 治理、容灾演练常态化 | ① 50 万座接入，稳态 1,700 msg/s 正常运行。② **连续 3 个月**接入 + 告警可用性 **≥ 99.95%**、遥测查询 + 报表 **≥ 99.9%**、OTA **≥ 99%**。③ 13 个月原始数据到期清理与 5 年聚合层查询在真实数据上验证通过，**应删已删核对差异为 0**。④ 每季度一次单 AZ 故障演练 + 一次数据恢复演练，全部留记录。⑤ 峰值 50,000 msg/s 至少验证 1 次 | 任一 SLO 连续 2 个月未达标则启动架构复审 |

## 7. 待人工拍板项（不得伪装成结论）

> 以下 8 项在本方案中已给出倾向性处理，但**均需业务方/架构评审委员会确认后方可进入 Phase 3**。
> 约束清单第 10 节声称"无待拍板项"，但下列缺口是在决策过程中被实际暴露出来的，其中 #1 正是约束清单自己举的例子，#7 是两份输入文件之间的实质矛盾。

| # | 待拍板项 | 为什么必须人工决定 | 若不确认的后果 | 本方案的临时处理 |
|---|---|---|---|---|
| 1 | **峰值 50,000 msg/s 是"必须无损承载的设计目标"还是"允许调度摊平的压测上限"** | 决定接入层与 Kafka 是否按 30 倍硬建，两者成本相差约 2 倍 | Phase 3 各图会采用不同假设，矛盾到 Phase 6 才暴露 | 按"必须无损承载"设计硬抗层，同时用令牌调度摊平可调度部分（两手都做，成本更高但更安全） |
| 2 | **单站日增 11 MB 中"文件类（录波）"与"结构化遥测"的占比；整站报文内是否携带秒级子采样** | 约束未给定。此比例决定 OSS 与 TSDB 的成本分工（相差约两个数量级）与 TSDB 写入吞吐设计（66,700 vs 4,000,000 样本/s） | 3.2 的全部成本数字失效；TSDB 选型与节点规模可能整体重算 | 按"40 点位 × 5 分钟单值"（读法 A）估算，并在 3.2 显式声明敏感性 |
| 3 | **告警 P99 < 10s 的度量终点与覆盖范围**：到达用户设备 vs 提交给推送网关；三通道是否都需 ≤ 10s；99.95% 是否排除"云侧完全中断"；离线补传告警是否通知、如何通知 | 短信运营商侧时延不可控；云侧全断时通知物理上不可达；补传告警通知是产品语义决策 | SLA 无法被客观判定，验收必然产生争议 | 定义为"成功提交给三通道网关"；99.95% 排除云侧全断场景；补传告警只入库并合并为离线汇总 |
| 4 | **客户侧 Ⅱ/Ⅲ 区隔离装置的落实情况与平台责任边界** | 横向隔离是合规红线，且依赖客户侧建设，平台无法单方达成 | 无法通过电力安全检查与等保测评，接入即违规 | 写为交付前置条件：未落实隔离装置的站点不得接入；网关不得跨区连接 |
| 5 | **自建 IoTDB vs 托管 Lindorm 的最终确认** | 取决于数据层运维人力评估（是否 ≥ 2 人全职）与 TCO 询价，这是组织能力与商务问题，不是技术问题 | 选型在实施中途翻案，数据链路返工 | 定 IoTDB，并写死回退触发条件（PoC 不达标或运维人力不足） |
| 6 | **EMQX 自建 vs 阿里云 MQTT 版的最终确认** | 取决于 50 万连接（双活后 100 万）+ 峰值 TPS 的托管规格报价与公司厂商锁定策略 | 接入层成本与可控性判断失真 | 定 EMQX 自建；托管报价低于自建 TCO 20% 以上时重议 |
| 7 | **北向数据输出的方向与范围** | **两份输入自相矛盾**：约束第 9 节写"平台作为数据消费方，通过 Modbus TCP / IEC 104 从边缘网关侧读取客户 SCADA/EMS"；能力清单域 7 写"北向数据输出供 SCADA/EMS 消费"。方向相反 | 可能凭空多建一个 `helios-northbound-service`（范围误增），或漏掉真实需求 | 按约束清单优先：主方向为"平台消费客户 SCADA/EMS 数据，协议解析在边缘运行时"；北向输出暂由 `openapi-gateway` 提供数据订阅 API，**不单列服务**，待确认后决定是否新建 |
| 8 | **成本上限与报表范围** | 约束未给成本约束，架构无法在"无上限"下做最优权衡；可用性目标提到"报表 99.9%"，但能力清单 8 个域中无独立"报表"能力，报表口径与范围未定义 | 分层策略、规格选择、报表服务的工作量都缺少判据 | 成本以 3.2 的估算作为基线提交评审；`helios-report-service` 按"读分钟/日聚合层 + 批量导出"的最小范围建设 |
