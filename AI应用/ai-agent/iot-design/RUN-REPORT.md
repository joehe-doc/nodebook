## 2. 流程被证明有效的四处

这四处是实跑中**真的抓到了问题**，不是理论推演。

### 2.1 「落盘 + 给路径」的委派机制成立，而且抓到了跨文件矛盾

`Plan` agent 拿到的只有两个文件路径，没有任何对话上下文。它读完后报出 **待拍板 #7：两份输入自相矛盾**。

- `00-constraints.md` 第 9 节：平台是客户 SCADA/EMS 的**数据消费方**（经边缘 Modbus TCP / IEC 104 读取）
- `01-capability-map.md` 域 7：写成了「北向数据输出**供 SCADA/EMS 消费**」

方向完全相反。这是我在 Phase 1 亲手写下的错误。

> **这条验证了 usage 手册 2.3 的核心主张**：把阶段产出各自成文件、委派时给路径，不只是省 token——**它让一个没有偏见的读者同时看到两份文档，从而发现我自己看不见的矛盾**。如果这两段内容都在对话历史里，我自己是发现不了的（我写的时候认为它们一致）。
>
> 也验证了 playbook 把 Phase 6 审查交给 fresh agent 的理由。只是这次矛盾在 Phase 2 就被抓到了，比 Phase 6 早两个阶段、便宜得多。

已修正：`01-capability-map.md` 升到 v1.1，并在第 5 节留了修订记录（含触发来源与裁定依据）。

### 2.2 命名表「从图里抽取」而非「先写后画」，当场拦住一处漂移

用 `grep -oE "helios-[a-z0-9-]+" docs/design.md | sort -u` 机械抽取，得到 23 个名字，再与 `02-decisions.md` 交叉核对：

- **服务名 100% 一致**，无同物异名，无幽灵服务。
- 唯一差异是 `helios-northbound-service`——而它在决策文档里是作为「**不要建**」出现的，于是进了命名表第 4 节「禁止创建名单」。这个副产物很有价值。
- **抓到 Kafka topic 缩写漂移**：两张图里 8 个 topic 全部写成 `uplink.raw` 这类缩写，而决策文档用全名 `helios.uplink.raw`。已裁定全名为准、缩写仅限那两张图的节点标签，并登记为 Phase 6 审查项。

> **这条验证了 playbook 6.3/6.4 的核心主张**：漂移在只有 2 张图时纠正成本极低；等到 Phase 4 画完 8 张图、每张各自缩写，成本会高一个量级。

### 2.3 「grep 查图标名，不要凭记忆写」不是锦上添花，是硬性要求

实跑中我凭记忆/类推写了 4 个图标名，**4 个全部不存在**：

| 我猜的名字 | 实际情况 | 正确名字 |
|---|---|---|
| `alibaba_cloud.mobile_client` | 不存在 | `aws4.mobile_client` |
| `alibaba_cloud.kms_key_management_service` | 不存在 | （无 KMS 图标；用 `cas_ssl_central_authentication_service`） |
| `alibaba_cloud.cloud_firewall` | 不存在 | `cfw_cloud_firewall` |
| `alibaba_cloud.ssl_certificates_service` | 不存在 | `cas_ssl_central_authentication_service` |

**猜测名的失败率是 4/4 = 100%。** 最终 60 种图标经脚本全量校验，0 个无效。

> usage 手册 2.2 那条规则的措辞应该更强硬。当前写的是"必须 grep"，但没说明失败率有多高——实跑数据是 100%。

### 2.4 Skill 上下文成本的判断被证实

- `mindmap` / `iot` / `cloud` 三个 skill 依次加载，体感无压力，与 usage 手册 2.1 的「每个 1.4~2.1K token，不用省着用」一致。
- 真正需要控制的是 stencils：**我全程只用 `grep`，一次都没有整读任何 stencil 文件**。如果整读 `aws4.md`（~19.5K token），单这一次就等于把三个 skill 的成本乘以十。

## 3. 发现的问题（按严重度排序）

### 🔴 3.1 Phase 2 → Phase 3 的闸门形同虚设，而且 Phase 0 的「无待拍板项」是个陷阱

`00-constraints.md` 第 10 节我写了「**待人工拍板项：无**」，还自我表扬说"9 个字段均已填实，可进入 Phase 1"。

`Plan` agent 返回后，待拍板项是 **8 个**。其中：

- #1（峰值 50,000 msg/s 是设计目标还是压测上限）**正是约束文档自己举的那个例子**——我写了"实际项目中此处通常会有 2~4 项待确认（例如……）"，然后宣称本项目没有。
- #2（11 MB/站/日 的文件 vs 结构化遥测占比）直接决定 TSDB 写入是 66,700 还是 4,000,000 样本/s，**相差 60 倍**，而约束里根本没给这个拆分。
- #8（成本上限、报表口径）是约束的**缺失字段**，我的 9 字段模板里压根没有这一项。

**结论**：`Phase 0 声称"无待拍板项"应该被视为红灯，而不是绿灯`。一次认真的 Phase 2 必然会暴露出若干个——因为 Phase 0 是人凭记忆写的，而 Phase 2 是拿着约束做真实计算。

按 usage 手册 5.3，本次**不该进入 Phase 3**。我为了验证流程越过了闸门，采用 `02-decisions.md` 第 7 节的临时处理继续，并把受影响的 4 项假设显式登记在 `docs/design.md` 3.3 节。

> **playbook 需要修订**：
> 1. Phase 0 的约束清单模板应**增加「成本上限」与「报表/BI 口径」两个字段**（当前 9 字段缺这两项，导致 #8）。
> 2. Phase 0 的退出标准应改为：「待拍板项一栏允许为空，但**必须写明"由 Phase 2 补充识别"**」，而不是让人误以为可以宣称"无"。
> 3. Phase 2 → Phase 3 的闸门需要一个**机械可判定的形式**，例如：`02-decisions.md` 末尾必须有一节「待拍板项处置」，逐项写明【已确认/采用临时处理+影响范围】，否则不得进入 Phase 3。当前的退出标准是散文式的，靠自觉。

### 🔴 3.2 渲染验证缺口——Phase 3 的一条退出标准本次无法满足

usage 手册 6.5 要求「在 Markdown Viewer 里实际渲染过，两张图都出图（不是方框）」。本机没有该扩展，**这条无法执行**。

我用一个 Python 脚本做了替代性的结构校验：

| 检查项 | 图 3-1 | 图 3-2 |
|---|---|---|
| `{` / `}` 配对 | 18/18 ✅ | 15/15 ✅ |
| `@startuml` / `@enduml` | 1/1 ✅ | 1/1 ✅ |
| 边中引用但未定义的别名 | **0 ✅** | **0 ✅** |
| 图标名在 stencils 中存在 | 60/60 ✅（修掉 1 个后） | 同 |

这四项覆盖了 PlantUML 最高频的错误类型，并且**真的抓到了 1 个 bug**（`mobile_client`）。但它**不等于渲染验证**：布局是否可读、连线是否糊成一团、`note` 位置是否压住节点，这些只有出图才知道。

> **playbook 需要修订**：把这个结构校验脚本作为 Phase 3/4 的**机械退出闸门**写进 usage 手册（当前只有散文式清单）。脚本很便宜，且能拦住凭记忆写图标名这一类 100% 失败率的问题。渲染目视检查保留为额外一条。

### 🟡 3.3 图规模超出 PlantUML 自动布局的舒适区

图 3-1 约 **40 个节点 / 55 条边 / 51 个别名**，图 3-2 约 **45 个节点 / 60 条边 / 65 个别名**。这个规模下 `left to right direction` 的自动布局很可能不理想（连线交叉、`note` 压节点、分组框重叠）。

playbook 完全没给「一张图最多放多少节点」的指导，也没给「什么时候该拆图、什么时候该换 `graphviz`」的判据。

> **playbook 需要修订**：增加一条经验阈值，建议 **单图 ≤ 25 个节点**；超过时优先按「主链路 / 旁路与治理」拆成两张，或改用 `graphviz`（`dot` 的自动布局对大图明显更稳，且 cluster 分组语义更强）。
> 本次两张图都应该拆：图 3-1 可拆为「上行数据主链路」+「下行控制与治理」；图 3-2 可拆为「网络分区与入口」+「ACK 三节点池与数据区」。

### 🟡 3.4 托管产品图标 vs 自建组件的语义陷阱（playbook 未覆盖）

`mxgraph.alibaba_cloud.kafka` 和 `realtime_compute` **都存在**，所以图标校验会通过。但它们指的是**阿里云托管产品**，而本项目用的是自建 Apache Kafka 与自建/托管混合的 Flink。用这两个图标会让读者误以为有云厂商 SLA 兜底。

这是一类**校验查不出来的错误**：名字有效，语义错误。

本次的处置（已写进 `03-naming-table.md` 第 7 节第 4 条）：
- `alibaba_cloud.*` 只用于真实使用的阿里云托管服务
- `kubernetes.sts`/`deploy`/`cronjob` 用于跑在 ACK 上的自建组件（`sts`=有状态、`deploy`=无状态、`cronjob`=批处理，这个区分本身携带「谁负责高可用与备份」的信息）
- `aws4.*` 用于与云厂商无关的通用实体（边缘网关、现场设备、外部系统、协议）

> **playbook 需要修订**：第 2.1 节的「图类型 → skill」表只解决了「用哪个 skill」，没解决「同一个 skill 内部选哪一类图标」。应补一条规则：**图标必须反映部署责任归属，而不只是"这个东西长得像什么"**。托管服务用云厂商图标，自建组件用 K8s 工作负载图标。

### 🟢 3.5 Phase 0 的交互性未被验证（本次验证的固有局限）

用户把 Phase 0 也交给了我，所以约束是我编的（虚构但自洽）。这意味着 **playbook 反复强调的「Phase 0 不能委派、要逐条追问」这一条，本次完全没有被测试**。

真实场景下 Phase 0 会是对话式的，而且追问质量直接决定后面所有阶段。3.1 节的 8 个待拍板项，本该有相当一部分在 Phase 0 的追问中就被问出来。

> 这条不是 playbook 的缺陷，是本次验证方式的局限。要验证它，需要一个真实项目、由业务方口述约束。

## 6. 结论

**流程可以跑通，且四个关键机制在实跑中都被证明有实际价值**（不是纸面正确）：

1. 阶段产出各自成文件 + 委派给路径 → 让 fresh agent 抓到了我自己在两份文档间制造的矛盾
2. 命名表从图里机械抽取 → 当场拦住 topic 缩写漂移，并副产出「禁止创建名单」
3. grep 校验图标名 → 拦住 1 个必然渲染失败的错误（凭记忆写的 4 个名字全错）
4. skill 按需唤起 + stencil 只 grep 不整读 → 上下文成本可控，实测与预估一致

**最需要修的是闸门**：Phase 0 的「无待拍板项」是个陷阱，Phase 2→3 的闸门是散文式的、靠自觉，本次就被我自己越过了。改成机械可判定的形式（第 4 节建议 1~4）是最高优先级。

**最需要补的是两条经验规则**：图标要反映部署责任归属（托管 vs 自建），以及单图节点数上限。这两条都是本次实跑撞出来的，playbook 原文没有。
